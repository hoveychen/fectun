# fectun

socat 式 TCP 端口映射,跨境段走 **FEC over UDP**。

用途:跨境链路存在**单向随机丢包**时,用前向纠错把丢包补回来,避免上层 TCP 因丢包降速。

## 为什么不用 kcptun

- 上游仓库 `xtaci/kcptun` 已 404(2026-07 实测,多个 fork 同样 404)
- 包格式自持,不带 KCP 协议特征,便于规避 DPI 识别

## 设计

```
[客户端] --TCP--> [fectun client] --FEC/UDP--> [fectun server] --TCP--> [目标服务]
```

四个要点:

1. **FEC(Reed-Solomon)** —— 每 k 个数据分片配 m 个校验分片,收到任意 ≥k 片即可重构全部数据
2. **NACK-based ARQ 兜底** —— TCP 字节流必须完整有序,FEC 未能恢复的残余丢包靠重传补齐。
   *不能省*:只有透明转发 TCP 包(VPN 式)才能靠上层 TCP 重传;本工具在本端终结连接、重建字节流,隧道自身必须可靠。
3. **心跳维持 conntrack** —— 阿里云安全组默认拒绝入站 UDP,实测单向 UDP 会被全丢;两端各 100ms 一次心跳,靠双向 conntrack 打通。
   心跳同时携带发送端 `nextSeq`,让对端能发现**尾部缺口**(否则最后一个包丢失时无后续包触发 NACK,直接死锁)。
4. **令牌桶限速** —— 实测持续满负载会把链路丢包从 10% 推到 30%,此时 75% 冗余的 FEC 也会崩。

## 使用

```bash
# 服务端(落地侧)
fectun -mode server -target 127.0.0.1:22 -peer <对端IP> -uport 55700 -k 20 -m 15 -rate 25

# 客户端(入口侧)
fectun -mode client -listen 0.0.0.0:4422 -peer <对端IP> -uport 55700 -k 20 -m 15 -rate 25
```

两端使用同一 UDP 端口便于打洞;本地回环测试可用 `-lport` 分开。

### 参数

| 参数 | 说明 |
|---|---|
| `-k` / `-m` | FEC 数据/校验分片数。`20:15` = 75% 冗余,按 22% 丢包设计 |
| `-rate` | **含冗余的线路限速(Mbps)**。净数据上限 ≈ `rate / (1+m/k)` |

**调参禁忌**:`-rate` 不要超过当时链路实际容量。曾把 rate 设到 60 Mbps(超出实测出口 28~48 Mbps),把入向打满、**SSH 被挤断**。

按丢包率选冗余度(实测信道外推):

| 配置 | 开销 | 9% 丢包残余 | 22% 丢包残余 |
|---|---|---|---|
| 10:3 | 30% | 0.78% | 11.25% ❌ |
| 20:10 | 50% | 0.001% | 1.88% |
| **20:15** | 75% | 0.000% | **0.073%** ✅ |

## 实测链路特性(阿里云 深圳 ↔ 韩国,2026-07-27)

- **丢包严格单向**:去程零丢包(80 Mbps 仍 0%),回程丢 6~22% 波动
- **近乎独立随机**:82.8% 为单包丢失,最长突发仅 4 包 → FEC 理想场景
- **短时与速率无关**:20/40/80 Mbps 下丢包率一致,故发冗余包不会加剧丢包
- **但持续满负载会恶化**:连续高强度对跑会把丢包推到 30%
- **ping 测不准**:ICMP 另有单独限速,丢包率(13~15%)与真实传输质量无关

实测 FEC 效果:线路丢包 10.8% → **FEC 后 0.0000%**,2500 组零失败,解码 CPU 开销 0.15%。

## 已知限制

- 无自适应冗余(丢包率波动时只能静态按最坏情况配)
- 无拥塞控制,靠固定令牌桶限速
- 发送缓冲按固定条数上限清理,极端乱序下可能误删待重传分片
- 小帧效率低:每个 mux 帧头单独占一个分片

## 何时**不该**用

若对端启用 BBR 且丢包在 ~10% 量级,BBR 直连往往已能跑满带宽,此时 FEC 的冗余开销反而拖慢吞吐。实测 10% 丢包下直连 24~27 Mbps、本工具 8.9~9.6 Mbps(受限速影响)。**FEC 的价值在链路劣化时兜底,不是提升峰值。**
